# Spec: Аудит токенов и observability для агента

Status: done

## Problem Statement

Владелец бота не видит, сколько токенов и на что тратит агент при обработке
сообщений: ни по каждому вызову модели, ни по запуску в целом, ни по классам
команд exec. Невозможно ответить на вопросы «какой запуск был дорогим»,
«какой контекст передаётся повторно», «что изменится, если я подкручу промпт
или историю». Любая оптимизация контекста делается вслепую: нет измерений до
и после, нет способа убедиться, что агент не стал хуже решать задачи.

## Solution

Observability-слой поверх существующего шва `InferenceProvider` и вокруг exec:
каждый вызов модели и каждый вызов инструмента записывается событием в JSONL
(и дублируется structlog-событием), запуск агента агрегируется в запись `run`.
CLI-отчёт рендерит из JSONL сводный dashboard и timeline конкретного запуска.
Повторно передаваемый контекст измеряется префиксным пересечением
последовательных запросов одного запуска. Фиксированный набор из 20
offline-задач прогоняется headless (без Telegram) против живого Ollama — это
эталон для сравнения до/после. Поверх измерений внедряются минимум три
оптимизации контекста; качество охраняется критерием «не больше одного
дополнительного сбоя» на бенчмарке, цель — сокращение суммарных токенов
(input+output) на запуск не менее чем на 30%.

## User Stories

1. Как владелец бота, я хочу видеть для каждого вызова модели модель, число input/output токенов и латентность, чтобы понимать ресурсоёмкость каждого шага агента.
2. Как владелец бота, я хочу видеть номер шага и id запуска в метриках каждого вызова, чтобы связывать расходы с конкретным местом в агентном цикле.
3. Как владелец бота, я хочу видеть для каждого exec класс команды, размеры ввода/вывода и длительность, чтобы находить команды, раздувающие контекст.
4. Как владелец бота, я хочу запись `run` на каждый запуск агента (шаги, суммарные токены, длительность, успех), чтобы сравнивать запуски между собой.
5. Как владелец бота, я хочу сводный dashboard по всем запускам (всего токенов, средний запуск, доля повторного контекста, top классов команд), чтобы оценивать общее потребление одним взглядом.
6. Как владелец бота, я хочу timeline конкретного запуска по его id (токены и команды по шагам), чтобы видеть, как растёт контекст от шага к шагу.
7. Как владелец бота, я хочу метрику доли повторно передаваемого контекста, чтобы измерять, сколько входных токенов модель уже видела.
8. Как владелец бота, я хочу оценку стоимости каждого запуска по настраиваемым ценам за токены, чтобы планировать перенос на облачного провайдера.
9. Как владелец бота, я хочу, чтобы метрики переживали рестарт бота, чтобы аудит не зависел от времени жизни процесса.
10. Как владелец бота, я хочу, чтобы в метриках и логах не было содержимого сообщений, ответов модели и выполняемых команд, чтобы приватность не нарушалась.
11. Как владелец бота, я хочу задавать цены input/output за 1M токенов через окружение, чтобы оценка соответствовала целевому провайдеру (по умолчанию локальная модель бесплатна).
12. Как владелец бота, я хочу топ классов exec-команд по доле токенов, чтобы целить оптимизации в главных пожирателей.
13. Как разработчик, я хочу мониторинг в виде декоратора на существующем шве `InferenceProvider`, чтобы слои и DI не нарушались.
14. Как разработчик, я хочу structlog-события с токенами и request_id, чтобы коррелировать метрики с обычным логом.
15. Как разработчик, я хочу, чтобы адаптер не выбрасывал счётчики токенов из ответа Ollama, чтобы данные были точными, а не оценочными.
16. Как владелец бота, я хочу фиксированный набор из 20 offline-задач в репозитории, чтобы сравнения до/после были воспроизводимыми.
17. Как владелец бота, я хочу headless-прогон бенчмарка напрямую через агентный цикл, чтобы измерения не требовали Telegram.
18. Как владелец бота, я хочу показатель success rate прогона (финальный ответ в пределах лимита шагов без ошибки), чтобы отличать «дешевле» от «сломаннее».
19. Как владелец бота, я хочу критерий «не больше одного дополнительного сбоя», чтобы шум малой выборки не прятал регрессии качества.
20. Как владелец бота, я хочу компакцию выводов инструментов старших шагов в сигнатуру «команда → ok/ошибка», чтобы контекст запуска рос линейно, а не квадратично.
21. Как владелец бота, я хочу настраиваемый порог компакции через окружение (с возможностью выключить), чтобы балансировать токены и качество без правки кода.
22. Как владелец бота, я хочу умную обрезку вывода exec (снятие ANSI/прогресс-шума, сохранение головы и хвоста), чтобы итоги и ошибки в конце выводов не терялись.
23. Как владелец бота, я хочу, чтобы третья оптимизация выбиралась по данным промежуточного аудита, чтобы рычаг выбирался по фактам, а не догадкам.
24. Как владелец бота, я хочу итоговый отчёт до/после в docs, чтобы результат аудита был зафиксирован и воспроизводим.
25. Как разработчик, я хочу обновлённый runtime-док с новыми настройками, чтобы конфигурация была документирована.

## Implementation Decisions

- **Единица учёта**: запуск агента = один агентный цикл (сообщение пользователя → финальный ответ или лимит шагов); `run_id` = `RequestId`; «turn» из задания = шаг. Термин «Запуск агента» уже внесён в глоссарий.
- **Контракт инференса**: `InferenceResponse` расширяется необязательными usage-полями: счётчик токенов промпта, счётчик выходных токенов, длительности. Адаптер Ollama парсит их из ответа `/api/chat` вместо выбрасывания. `reasoning_tokens` фиксируется нулём: API его не отдаёт, при think-режиме размышления уже внутри выходных токенов.
- **Мониторинг LLM**: декоратор, реализующий Protocol `InferenceProvider`; композиционный корень оборачивает в него реальный провайдер. Декоратор не знает ни про Telegram, ни про Ollama.
- **Мониторинг exec**: метрика вызова инструмента строится вокруг выполнения команды в харнессе: класс команды, размеры ввода/вывода, длительность, оценка выходных токенов.
- **Классификация команд**: чистая функция по первому слову/паттерну: `git`, `python`/`pytest`, `rg`/`grep`, `cat`/`sed`, `ls`, прочее; метрика записывается как `exec:<класс>`.
- **Повторный контекст**: префиксное пересечение последовательных запросов одного запуска считается по символам на списках сообщений, доля пересечения умножается на точный счётчик токенов промпта — оценка повторных токенов. Эта же доля публикуется в dashboard как cache hit rate (прямых данных кэша Ollama не существует — проверено на 0.33).
- **Хранение**: append-only JSONL в фиксированном каталоге данных метрик (`.data/metrics/`, вне Git, создаётся при первой записи): события `llm_call`, `tool_call`, `run`. Каждое событие дублируется structlog-событием с `request_id`. Содержимое сообщений, команд и ответов не записывается нигде — только id, счётчики, размеры, статусы.
- **Оценка стоимости**: цены input/output за 1M токенов — настройки из окружения, по умолчанию 0 (локальная модель бесплатна, в отчёте честно `$0.00`).
- **Dashboard**: CLI-команда (`uv run python -m bot.report`): агрегат по всем запускам и timeline по `--task <id>`; текстовый вывод в формате из задания. Никаких новых поверхностей в Telegram.
- **Бенчмарк**: 20 offline-детерминированных задач в репозитории: 5 «из знаний», 5 одношаговых exec, 6 многошаговых по репозиторию, 4 смешанных. Прогон headless через агентный цикл против живого Ollama. Success = финальный ответ в пределах лимита шагов без ошибки. Сетевых задач нет — сравнение должно зависеть только от наших изменений.
- **Критерии приёмки**: экономия = средние суммарные токены (input+output) на запуск, цель ≥30%; охрана качества = не больше одного дополнительного сбоя на наборе из 20 задач.
- **Оптимизация 1 — компакция**: в рабочем множестве запуска выводы инструментов шагов старше K=3 схлопываются в сигнатуру «команда → ok/ошибка» (без тела вывода; модель может перечитать командой). Порог — настройка из окружения, 0 = выключено. Компакция выполняется при сборке запроса; хранимая чат-сессия не меняется (она tool-обмен и так не хранит).
- **Оптимизация 2 — обрезка exec-вывода**: вместо простого среза по лимиту символов — снятие ANSI/прогресс-шума и сохранение головы+хвоста вывода в пределах того же лимита.
- **Оптимизация 3 — по данным**: выбирается после первого прогона бенчварка с мониторингом из списка: динамическое окно истории по токенам; чтение обычных файлов фрагментами (правка системного промпта); сжатие системного промпта. Скиллы не трогаются: индекс уже минимальный (имя + описание), полный файл читается по требованию — это подтверждено кодом.
- **Документация**: новые настройки окружения дополняют runtime-док; итоговый отчёт до/после — отдельный документ в docs.
- **Поставка**: PR №1 — мониторинг, dashboard, бенчмарк, baseline-прогон; PR №2 — оптимизации и отчёт до/после. Перед каждым PR — все четыре гейта (ty, ruff check, ruff format --check, pytest).

## Testing Decisions

- Тестируется внешнее поведение: что записано в JSONL, какие запросы увидел провайдер, что вернул инструмент, что напечатал рендер. Внутреннее устройство декоратора и хелперов не тестируется.
- Швы (все существующие, один новый сидит на существующем Protocol-шве):
  1. Декоратор поверх `InferenceProvider`: в тестах заворачивает `ScriptedInferenceProvider` из тестовых дублей; проверяются поля событий `llm_call` и агрегат `run`.
  2. `AgentLoop.run()`: скриптованный провайдер запоминает полученные запросы; проверяются run-запись и компакция (старшие tool-выводы приходят схлопнутыми, последние K — целиком).
  3. Exec-инструмент: реальные команды с ANSI-шумом; проверяются обрезка голова+хвост и событие `tool_call` с классом команды.
  4. Чистые функции напрямую: классификация команд, префиксное пересечение, рендер dashboard; JSONL в тестах пишется во временный каталог.
- Prior art: существующие тесты цикла и exec в `tests/unit/agent/`, тесты адаптера в `tests/unit/inference/`, общие дубли в `tests/fakes.py`. Новые тесты ложатся по соседству (каталоги под metrics уже ждут наполнения).
- Бенчмарк и baseline — не unit-тесты: ручной локальный прогон против живого Ollama; результат фиксируется в baseline-отчёте PR №1 и отчёте до/после PR №2.

## Out of Scope

- Веб-dashboard, HTML, команды статистики в Telegram.
- Реальный cache hit Ollama и reasoning-токены из API: источник данных не отдаёт ни того, ни другого (проверено); публикуется честная прокси-метрика повторного контекста.
- Сетевые/weather-задачи в бенчмарке: сетевой шум некоррелируемо влиял бы на success rate до/после.
- Изменение дизайна скиллов (индекс, подгрузка файла целиком).
- Реальные деньги по умолчанию: цены настраиваются, но стартуют нулём; выдуманные прайсы не подставляются.
- Латентность инференса как цель оптимизации (скорость загрузки модели, прогрев) — замеряется, но не оптимизируется.
- ADR: все принятые решения обратимы настройками, критерии ADR не выполняются.

## Further Notes

- Факты об окружении, на которых построена спека: Ollama 0.33 отдаёт только счётчики промпта/вывода и длительности; экспериментально подтверждено, что счётчик промпта — весь промпт, а не только некэшированная часть. Адаптер сегодня парсит только сообщение и выбрасывает остальные поля.
- Главный потребитель input в текущем коде — рабочее множество текущего запуска: полный tool-обмен пересылается на каждом шаге; чат-сессия хранит только реплики диалога. Поэтому компакция и обрезка бьют по самой жирной статье.
- Системный промпт мал (~700–800 токенов с датой и индексом скиллов) — его сжатие слабый рычаг, поэтому третья оптимизация выбирается по данным.
- Бенчмарк требует живого Ollama с моделью qwen3:1.7b; в CI не переносится, это локальный этап владельца.
