# Spec: Минимальный AI-агент (Minimal Agent)

**Status:** ready-for-agent

Превращение Telegram-бота с одним LLM-запросом в автономного агента: харнесс с агентным циклом, инструмент exec, скиллы и чат-сессии. Терминология — по глоссарию `CONTEXT.md`.

## Problem Statement

Бот сегодня — это «текст в → текст out»: модель не может выполнять действия в системе (запустить CLI, сходить curl-ом в API), каждое сообщение обрабатывается независимо (модель ничего не помнит о предыдущих сообщениях чата), а про длинные инструкции/рутины думать нечего — их негде хранить и некому исполнять.

## Solution

Бот становится агентом: сообщение пользователя запускает агентный цикл, в котором модель либо отвечает финальным ответом, либо запрашивает выполнение консольной команды через инструмент exec (харнесс выполняет её и возвращает результат модели, цикл продолжается). Диалог каждого Telegram-чата — одна чат-сессия (единый длинный контекст), сбрасываемая командой /new. Специализированные инструкции живут как скиллы в `skills/`: модель видит их индекс в системном промпте и при необходимости читает файл сама через exec. Пользователь наблюдает шаги агента (⚙️/✅) и получает финальный ответ, разбитый на сообщения телеграм-совместимой длины.

## User Stories

1. As a владелец бота, I want чтобы модель могла выполнять консольные команды в системе, so that агент решал реальные задачи, а не только рассуждал текстом
2. As a владелец бота, I want чтобы цикл «модель → инструмент → модель» повторялся до финального ответа, so that многошаговые задачи доводились до конца без моего участия
3. As a владелец бота, I want защиту от зацикливания (лимит шагов), so that зависшая модель не крутилась вечно и не тратила ресурсы
4. As a владелец бота, I want честное сообщение при достижении лимита шагов, so that я понимал, что агент остановился, и мог продолжить уточняющим сообщением
5. As a владелец бота, I want чтобы история диалога хранилась как одна чат-сессия на чат, so that контекст не терялся между сообщениями
6. As a владелец бота, I want команду /new, so that я мог начать свежий разговор без старого контекста
7. As a владелец бота, I want чтобы при переполнении окна истории брались последние N сообщений, so that длинные разговоры не ломали контекст модели
8. As a владелец бота, I want чтобы при обрезке истории пара «вызов инструмента → результат» не разрывалась, so that запрос к модели оставался валидным
9. As a владелец бота, I want видеть ⚙️ с командой перед её выполнением, so that я понимал, что агент сейчас делает
10. As a владелец бота, I want чтобы сообщение шага редактировалось в ✅ после выполнения, so that лента чата читалась как чистый журнал
11. As a владелец бота, I want длинные финальные ответы, разбитые на несколько сообщений, so that Telegram не отвергал их из-за лимита в 4096 символов
12. As a владелец бота, I want скиллы как markdown-файлы с инструкциями, so that я добавлял агенту новые умения правкой файла, а не кода
13. As a владелец бота, I want чтобы модель видела только индекс скиллов (имя + описание), so that системный промпт не разбухал с ростом числа скиллов
14. As a владелец бота, I want чтобы модель сама читала файл скилла через exec по необходимости, so that инструкция попадала в контекст только когда нужна
15. As a владелец бота, I want скилл-рутину «погода в Минске» (curl wttr.in → сводка по-русски), so that я получил готовый пример Типа B и мог проверить весь конвейер
16. As a владелец бота, I want ограничение списка чатов (allowlist), so that неизвестные пользователи не могли выполнять команды на моей машине
17. As a владелец бота, I want таймаут на выполнение команды, so that зависшая команда не блокировала агента навсегда
18. As a владелец бота, I want обрезку длинного вывода команд, so что вывод не съедал контекст маленькой модели
19. As a владелец бота, I want чтобы модель получала exit code + stdout + stderr, so that могла сама диагностировать неудачные команды и исправляться
20. As a владелец бота, I want последовательную обработку сообщений одного чата (блокировка), so that параллельные сообщения не ломали историю сессии
21. As a владелец бота, I want нативные tool-calls модели, so что вызовы инструментов были надёжными без текстовых протоколов и парсинга
22. As a владелец бота, I want обновлённый текст /start, so что я сразу видел возможности агента и команду /new
23. As a разработчик, I want лимит шагов, размер окна и таймауты как переменные окружения, so that я подстраивал их без правки кода
24. As a разработчик, I want расширение контракта инференса (tools, tool-сообщения), so that агентный цикл тестировался на фейковом провайдере без сети и Ollama
25. As a разработчик, I want порт исполнителя команд в application-слое, so that поведение exec (таймаут, обрезка) тестировалось изолированно от shell
26. As a разработчик, I want сохранение слоистой архитектуры, so что Telegram не знал про Ollama, а приложение не знало про aiogram и shell

## Implementation Decisions

- Один путь обработки: `process_message` заменяется агентным циклом; «простое» сообщение — частный случай (первый ответ без tool-calls = финальный ответ).
- Протокол инструментов: нативный `tools`-параметр Ollama `/api/chat`; ответ модели несёт `tool_calls` (имя + JSON-аргументы), результат возвращается сообщением с новой ролью `tool`. Контракт инференса расширяется: роль `tool`, поля tool-calls в сообщении, список описаний инструментов в запросе.
- Модель: `qwen3:1.7b`, режим размышлений (`think`) отключён — «думания» в контенте быть не должно; смена модели — переменной окружения.
- Агентный цикл: шаг = один ответ модели; ответ с tool-calls → выполнить инструменты → продолжить; ответ без tool-calls → финальный ответ. Лимит шагов по умолчанию 10 (`AGENT_MAX_STEPS`); при превышении — честное сообщение пользователю, цикл останавливается.
- Инструмент exec: одна строка команды в shell; рабочий каталог — корень проекта; таймаут по умолчанию 60 с (`AGENT_TOOL_TIMEOUT_SECONDS`); результат модели = exit code + stdout + stderr, суммарно обрезанный до ~4000 символов. Подтверждения пользователем нет — автономность; единственное смягчение — allowlist чатов (ADR не оформлялся, решение задокументировано здесь).
- Чат-сессия: один файл на чат `.data/chats/<chat_id>.jsonl` (append-only, каталог в .gitignore); окно — последние 20 сообщений (`AGENT_HISTORY_MAX_MESSAGES`), срез смещается до границы пары «вызов → результат»; системный промпт не хранится — собирается заново при каждом запросе (индекс скиллов актуален). `/new` обрезает файл сессии.
- Параллельность: блокировка на чат — второе сообщение ждёт завершения первого цикла.
- Скиллы: каталог `skills/`; в системный промпт — индекс (имя + краткое описание); полный текст модель читает сама через exec. Первый скилл — Тип B «погода»: curl `https://wttr.in/Minsk?1`, сводка по-русски.
- Telegram-слой: перед командой сообщение `⚙️ $ <команда>`, после выполнения оно редактируется в `✅`; финальный ответ — plain text (без Markdown-парсинга), сплит на части ~4000 символов по границам строк; `/new` регистрируется отдельным хендлером.
- Allowlist: `TELEGRAM_ALLOWED_CHAT_IDS` (список через запятую); пусто — бот отвечает всем (текущее поведение), заполнено — чужие чаты молча игнорируются.
- Обновляются текст `/start` и README (описание агента, чат-сессии, /new, новые переменные окружения).
- Слои сохраняются: харнесс и цикл — в application-слое; shell-исполнитель и Ollama-сериализация tools — инфраструктурные адаптеры; Telegram-хендлеры не знают про инструменты.

## Testing Decisions

- Хороший тест проверяет внешнее поведение на швах, а не внутренности: фейковые двойники на границах (инференс, исполнитель команд, Telegram), реальные файловые операции на временных каталогах.
- Шов 1 (существующий, расширяется) — контракт инференса: фейковый провайдер со скриптованными ответами (tool-calls → финальный ответ) проверяет цикл целиком: завершение, лимит шагов, накопление истории, целостность пар.
- Шов 2 (новый) — порт исполнителя команд в application-слое: цикл тестируется с фейковыми результатами; реальный shell-адаптер — отдельно (таймаут, обрезка, exit code, stdout/stderr) на быстрых командах.
- Хранилище чат-сессий: реальная файловая система во временном каталоге — append, окно, срез по границе пар, обрезка при /new.
- Сплиттер сообщений и индекс скиллов — чистые функции, табличные тесты.
- Telegram-хендлеры (/new, allowlist, ⚙️→✅) — с подменённым сервисом по образцу существующих тестов хендлеров.
- Сериализация tools/tool-сообщений в Ollama-адаптере — httpx MockTransport по образцу существующих тестов адаптера.
- Integration-тест полного цикла Telegram → приложение → Ollama без сети — по образцу существующего.

## Out of Scope

- ADR «exec без подтверждения» (решение зафиксировано в спеке; можно оформить позже)
- Скилл Типа A (инструкция к CLI/API) — только погодная рутина Типа B
- Персистентность сложнее JSONL (БД, архивирование старых сессий)
- Sandbox, подтверждение команд, ограничение команд exec
- Стриминг ответов, Markdown-разметка ответов
- Подсчёт токенов для окна истории (только счётчик сообщений)
- Дополнительные инструменты кроме exec, дополнительные провайдеры инференса
- Мульти-контекстность проекта (репо остаётся single-context)
