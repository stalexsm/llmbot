# Spec: RAG — работа агента с документами пользователя

**Status:** done

Расширение Telegram-агента: пользователь присылает документы, агент отвечает на вопросы по их содержимому через самостоятельно реализованный RAG-pipeline на SQLite + sqlite-vec. Терминология — по глоссарию `CONTEXT.md` (Документ, Владелец, Чанк, Эмбеддинг, Индексация, Источник); решения об изоляции и хранении зафиксированы в ADR-0002 и ADR-0003.

## Problem Statement

Агент отвечает только из общих знаний модели и текста разговора. Пользователь не может передать боту свои материалы (регламенты, инструкции, заметки) и получить ответы с опорой именно на них: нет способа загрузить документ, спросить по нему, узнать, из какого места документа взят ответ, и убрать документ, когда он больше не нужен. Ответы модели на вопросы о содержимом документов либо отсутствуют, либо выдумываются из общих знаний — без указания источника им нельзя доверять.

## Solution

Пользователь отправляет боту файл (`.txt`, `.md`, `.docx`, `.pdf`); бот извлекает текст, разбивает его на чанки, получает эмбеддинги и складывает их в SQLite с векторным индексом. После индексации пользователь спрашивает обычным сообщением; агент сам решает, когда вопрос требует поиска, вызывает инструмент поиска по документам, получает релевантные чанки своего корпуса и отвечает с указанием источника. Если ответа в документах нет — агент честно это говорит. Пользователь видит список своих документов, удаляет ненужные, следит за прогрессом обработки больших файлов, а вопросы с местоимениями («а можно перенести их на следующий год?») понимаются с учётом истории разговора. Корпуса разных владельцев изолированы: поиск никогда не выходит за пределы документов одного пользователя.

## User Stories

1. Как пользователь, я хочу отправить боту файл `.txt`, `.md`, `.docx` или `.pdf`, чтобы агент отвечал на вопросы по его содержимому.
2. Как пользователь, я хочу получить подтверждение, что документ получен и началась обработка, чтобы понимать, что файл дошёл и принят.
3. Как пользователь, я хочу видеть прогресс индексации по стадиям (извлечение текста → количество чанков → эмбеддинги → готово), чтобы знать, что происходит с большим документом и что бот не завис.
4. Как пользователь, я хочу получить сообщение о готовности документа, чтобы знать, когда можно задавать вопросы.
5. Как пользователь, я хочу задавать вопросы по содержимому документа обычными сообщениями, не изучая специальных команд.
6. Как пользователь, я хочу, чтобы агент сам решал, когда вопрос требует поиска по документам, чтобы не указывать это явно в каждом вопросе.
7. Как пользователь, я хочу видеть в ответе Источник (имя документа), чтобы проверять, откуда взята информация.
8. Как пользователь, я хочу видеть страницу PDF-источника, чтобы находить место в оригинальном документе.
9. Как пользователь, я хочу искать по всем своим документам сразу, чтобы не указывать, в каком файле искать.
10. Как пользователь, я хочу, чтобы вопрос с местоимениями учитывал предыдущий разговор («Сколько дней отпуска? — А можно перенести их на следующий год?»), чтобы не переформулировать каждый вопрос с нуля.
11. Как пользователь, я хочу честный ответ «не нашёл этой информации в загруженных документах», когда ответа в корпусе нет, чтобы отличать «нет в документах» от «модель не знает».
12. Как пользователь, я не хочу, чтобы общие знания модели выдавались за содержимое моих документов, чтобы доверять ответам с атрибуцией.
13. Как пользователь, я хочу команду `/documents`, чтобы видеть список документов своего корпуса.
14. Как пользователь, я хочу команду `/delete` с именем файла, чтобы убрать документ, когда он больше не нужен.
15. Как пользователь, я хочу, чтобы при удалении документа вычищались и его чанки с эмбеддингами, чтобы удалённое не находилось в поиске.
16. Как пользователь, я хочу при `/delete` несуществующего имени получить дружелюбную ошибку со списком доступных документов, чтобы понять, что удалить.
17. Как пользователь, я хочу, чтобы повторная отправка файла с тем же именем заменяла старую версию, чтобы обновить документ без ручного удаления.
18. Как пользователь, я хочу, чтобы загрузка во время индексации предыдущего документа не ломала ничего, а просто ждала своей очереди.
19. Как пользователь, я хочу задавать вопросы, пока идёт индексация, и быть уверенным, что ответ не смешает старую и новую версии документа.
20. Как пользователь, я хочу понятное сообщение при неподдерживаемом формате файла, вместо молчания или stack trace.
21. Как пользователь, я хочу понятное сообщение при повреждённом PDF или DOCX, чтобы понять, что дело в файле, а не в боте.
22. Как пользователь, я хочу понятное сообщение при пустом документе, чтобы узнать, что текста извлечь не удалось.
23. Как пользователь, я хочу понятное сообщение при слишком большом документе, чтобы знать, что файл не вместится.
24. Как пользователь, я хочу, чтобы сбои эмбеддинг-модели, LLM, SQLite, Telegram API и таймауты превращались в понятные сообщения, а бот продолжал работать.
25. Как владелец документа, я хочу, чтобы мой корпус был изолирован: поиск другого пользователя никогда не видел моих документов, чтобы личные файлы оставались личными.
26. Как владелец документа, я хочу продолжать обычный диалог с агентом (exec, скиллы) без документов, чтобы RAG не мешал существующим сценариям.
27. Как пользователь, я хочу, чтобы индексация шла в фоне, чтобы чат не блокировался на время обработки большого PDF.
28. Как агент, я хочу инструмент поиска по документам с явным скоупом владельца, чтобы находить чанки только корпуса спрашивающего.
29. Как агент, я хочу получать вместе с чанками их источники и явный признак «ничего не найдено», чтобы строить честные ответы с атрибуцией.
30. Как агент, я хочу правило в системном промпте: отвечать на вопросы о документах только результатом инструмента, чтобы не выдумывать.
31. Как разработчик, я хочу порт эмбеддингов по образцу существующего контракта инференса, чтобы подменять модель в тестах и менять провайдера без изменения верхних слоёв.
32. Как разработчик, я хочу расширить контракт инструмента контекстом выполнения (скоуп владельца), чтобы изоляция была частью контракта, а не фактом сборки.
33. Как разработчик, я хочу хранить чат-сессии в SQLite с прежним контрактом хранилища (`load`/`append`/`reset`), чтобы оба постоянных состояния жили на одном движке, а application-слой не заметил подмены.
34. Как разработчик, я хочу датасет оценки retrieval (вопросы с известными источниками) и команду его прогона против живой модели, чтобы измерять, что поиск действительно возвращает правильные чанки.
35. Как разработчик, я хочу минимум пять автотестов на нескольких уровнях (парсинг, чанкинг, retrieval + изоляция, e2e), проходящих без живого Ollama, чтобы регрессии ловились в CI-гейтах.
36. Как разработчик, я хочу учёт вызовов поиска в существующих метриках инструментов без записи содержимого запросов, чтобы наблюдать нагрузку RAG, не нарушая политику логирования.
37. Как разработчик, я хочу README с обоснованиями выбора (размер чанка, overlap, модель эмбеддингов, метрика и K, схема хранения, изоляция, ограничения), чтобы выбор можно было проверить и оспорить.
38. Как разработчик, я хочу бинарные фикстуры PDF/DOCX в репозитории, чтобы тесты парсинга были детерминированными и не требовали генерации на месте.

## Implementation Decisions

**Слои.** RAG — новый верхнеуровневый слой между application/agent и хранилищем: полный pipeline «извлечение → чанкинг → эмбеддинги → хранение → поиск». Правило границ расширяется: `Telegram ≠ Application ≠ Agent ≠ Inference ≠ RAG ≠ Ollama`; `docs/architecture.md` обновляется. Потребители слоя — application (сценарий индексации, команды документов) и agent (инструмент поиска).

**Эмбеддинги.** Новый `EmbeddingProvider` — Protocol в inference-слое, зеркало `InferenceProvider`; адаптер Ollama (`/api/embed`, батчевая обработка чанков). Модель — `bge-m3`, 1024 измерения: локально, бесплатно, лучшее качество на русском среди доступных локально. Модель скачивается один раз отдельно (`ollama pull`); бот при отсутствии модели отдаёт понятную ошибку.

**Владелец и изоляция** (ADR-0002). Владелец Документа — `TelegramUserId` (NewType поверх Telegram `from_user.id`); сессии, allowlist и блокировка обработки остаются chat-scoped. Скоуп владельца доходит до инструментов как явный контекст выполнения: контракт `Tool` расширяется параметром контекста, который агентный цикл прокидывает из application-слоя; существующий exec-инструмент контекст игнорирует. Поиск фильтруется по владельцу до/при KNN (переопрос с запасом + фильтр), изоляция — обязательный тест.

**Хранение** (ADR-0003, `.data/rag.db`). SQLite + sqlite-vec: таблицы `documents` (id, владелец, имя файла, тип, created_at) → `chunks` (id, документ, порядковый номер, текст, страница) → виртуальная таблица векторов vec0 с обратной ссылкой на чанк. Косинусная метрика, K=5 с внутренним переопросом. Повторная загрузка имени — атомарная замена (старые документ/чанки/векторы удаляются, новые появляются одной транзакцией). Сырой файл после индексации не хранится. Rag-БД и chats-БД — отдельные файлы; каждый слой владеет своей схемой и соединением; sqlite-vec грузится только на rag-соединение.

**Чат-сессии на SQLite** (ADR-0003). Контракт хранилища сессий (`load`/`append`/`reset`) не меняется — подменяется только реализация: отдельный файл `.data/chats.db`, stdlib `sqlite3` синхронно, таблица `messages` (id, chat, роль, текст, created_at), окно — последние N по убыванию id, `/new` — удаление по чату. Хранимое не меняется: только диалог «пользователь ↔ финальный ответ». Существующие JSONL-истории не импортируются. Метрики остаются append-only JSONL (анализ в комментариях сессии).

**Чанкинг.** Структурно-осведомлённое разбиение: границы абзацев и заголовков Markdown, страницы PDF; мелкие куски склеиваются до целевого размера ~900 символов, overlap ~150 символов; для PDF чанк привязан к странице (даёт Источник со страницей). Параметры — в конфиг, обоснование — в README.

**Инструмент поиска и промпт.** `search_documents` — инструмент за существующим контрактом `Tool`, регистрируется рядом с exec; вызовы учитываются существующим декоратором метрик инструментов (без содержимого запросов). Системный промпт дополняется правилами: вопросы о документах — через инструмент; отвечать только найденным; при «ничего не найдено» — честно сообщить; указывать Источник.

**Порог «не найдено».** Поиск возвращает top-K, но ниже настраиваемого порога косинусной близости инструмент отдаёт модели явное «ничего не найдено». Стартовое значение калибруется на evaluation-датасете.

**Conversation-aware (бонус).** Перед поиском инструмент делает один короткий LLM-вызов переписывания: вопрос + последние реплики диалога → самостоятельный Поисковый запрос. Порт `QueryRewriter` объявлен в rag-слое, реализация — поверх существующего `InferenceProvider` (та же чат-модель) в композиционном корне. Переписывание выполняется всегда; при сбое — поиск по сырому вопросу. История в контексте ответа и так есть — окно диалога агентного цикла.

**Прогресс и фоновая индексация (бонусы).** Обработчик Telegram мгновенно подтверждает приём и открывает индексацию фоновой задачей; прогресс — один редактируемый статус-месседж со сменой стадий (троттлинг правок ~1.5 с; если правка невозможна — новое сообщение). Индексации одного владельца сериализуются блокировкой; вопросы во время индексации видят старый корпус — замена атомарна. Ошибки индексации уходят тем же статус-месседжем, работа бота не прерывается.

**Лимиты и команды.** Лимиты конфигурируемы: файл ≤ 20 MB (потолок Bot API), извлечённый текст ≤ 200k символов, ≤ 300 чанков. `/documents` — список корпуса владельца; `/delete <имя>` — без подтверждения, при неизвестном имени — ошибка со списком. Все сообщения пользователю — на русском, в стиле существующих.

**Зависимости и документация.** Новые зависимости: `sqlite-vec`, `pypdf`, `python-docx`. Обновляются: `README` (архитектура, chunking, embeddings, retrieval, storage, security, limitations), `docs/architecture.md` (новый слой, контракты, поток сообщения, chats-БД), `env.example` (новые настройки), глоссарий и ADR уже обновлены. RAG-фреймворки, скрывающие pipeline, не используются — всё от извлечения до контекста реализуется самостоятельно.

## Testing Decisions

Хороший тест проверяет внешнее поведение через контракты слоёв, а не внутренности: реализацию хранилища, параметры SQL, структуру промпта тест не знает. Швы утверждены пользователем; новых *видов* швов нет.

- **Шов 1 — application-сценарии** (наивысший): индексация в фоне под блокировкой владельца, атомарная замена, списки и удаление. Фейки: `EmbeddingProvider` (детерминированные векторы), прогресс; SQLite реальный, во временном файле. Предшественник — существующие интеграционные тесты application-сценариев.
- **Шов 2 — `InferenceProvider`**: e2e по существующему шаблону — скриптованные ответы модели «вызов `search_documents` → финальный ответ с Источником» через агентный цикл; Telegram замокан. Проверяется полный путь: индексация → вопрос → retrieval → ответ.
- **Шов 3 — контракт `Tool`**: `search_documents` как любой инструмент — `ToolResult` с чанками/источниками, «не найдено» ниже порога, поведение при сбое переписывания запроса. Здесь же тест изоляции: владельцы A и B, поиск A никогда не возвращает чанки B.
- **Шов 4 — чистые функции**: извлечение текста для четырёх форматов (бинарные фикстуры коммитятся) и чанкинг (границы, overlap, привязка страниц) — прямые unit-тесты по конвенции репо (как тесты окна истории).
- **Шов 5 — хранилище сессий**: контракт `load`/`append`/`reset` прежний — существующие тесты сессий продолжают проходить с временным файлом БД; это одновременно проверка заявления ADR-0003.

Минимум задания (5 тестов) перекрывается с запасом. Evaluation — отдельный запуск против живого Ollama: датасет ≥ 5 вопросов с известными источниками, отчёт «вопрос → найденные чанки → попадание», заодно калибровка порога; без живого сервера тест пропускается.

## Out of Scope

- Гибридный поиск (FTS + слияние) и реранкинг — бонусы задания, сознательно не берём (решение раунда 1).
- Перевод метрик на SQLite — остаются append-only JSONL (анализ: write-once-лог, выгоды БД на этом объёме неизмеримы).
- Импорт существующих JSONL-историй в chats-БД.
- Хранение сырых файлов после индексации.
- Мультиарендность beyond изоляции владельцев: совместные корпуса, шаринг документов между пользователями, роли.
- Эмбеддинги через внешние API — только локальная модель.
- Готовые RAG-фреймворки — pipeline реализуется самостоятельно (ограничение задания).
- Доска прогресса в групповых чатах, локализация сообщений на другие языки.

## Further Notes

- Источник требований — «Домашнее задание — RAG для AI-агента.md» в корне репо; при эволюции формулировок правила фиксируются в ADR и `docs/`, сам файл не редактируется.
- Перед реализацией один раз выполнить `ollama pull bge-m3` (~1.2 GB); без модели интеграционные сценарии RAG деградируют в понятные ошибки — это штатно.
- Acceptance criteria задания (чек-лист из 18 пунктов) покрываются user stories 1–25 и тестами; на защите демонстрируются загрузка, индексация, ответ с Источником, «не нашёл», несколько документов, изоляция двух пользователей, удаление, тесты, evaluation.
- Реализация разбивается на тикеты отдельной задачей; предлагаемый порядок: зависимости/конфиг → чат-сессии на SQLite → rag-слой → инструмент и промпт → application → Telegram → тесты/evaluation → документация.
