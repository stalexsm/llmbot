# 05: Conversation-aware — переписывание запроса (бонус +2)

**What to build:** вопросы с местоимениями и контекстом («Сколько дней отпуска?» → «А можно перенести их на следующий год?») находят правильные чанки: перед поиском выполняется один короткий LLM-вызов, который по вопросу и последним репликам диалога строит самостоятельный поисковый запрос. Порт переписывания объявляется в rag-слое, реализация — поверх существующего провайдера инференса (та же чат-модель) в композиционном корне; границы слоёв не нарушаются. Переписывание выполняется всегда (дёшево и предсказуемо); при сбое поиск идёт по сырому вопросу.

**Blocked by:** 04 (search_documents как инструмент агента)

**Status:** done

- [x] Сбой переписывания не рвёт поиск: используется сырой вопрос, пользователь ответ получает

## Comments

- Порт: `QueryRewriter` (`bot/rag/rewrite.py`) — `rewrite(request_id, question, recent_turns) -> str`; исключение от реализации — легальный исход, вызывающая сторона обязана упасть на сырой вопрос. Реализация `LlmQueryRewriter` — в композиционном корне (`bot/main.py`): тот же чат-модель (`settings.ollama_model`) поверх декоратора метрик, короткий системный промпт, ответ чистится от кавычек; пустой ответ — возврат сырого вопроса (не сбой).
- Поток данных: `ApplicationService` рендерит реплики диалога («Роль: текст», история окна + текущий вопрос) в `ExecutionContext.recent_turns` (расширение `domain/tools.py`) → `AgentLoop` прокидывает контекст инструментам → `SearchDocumentsTool` вызывает переписывание перед `rag.search` и при любом исключении логирует `query_rewrite_failed` (только request_id) и ищет по сырому запросу. `RagService` не изменился.
- E2E на скриптованном провайдере: сообщение «Сколько дней отпуска?» → уточнение «А можно перенести их на следующий год?» — модель вызывает поиск с сырым уточнением, переписывание возвращает «перенос отпуска на следующий год», эмбеддинг попадает на ось «отпуск» и находит чанк, который сырой уточняющий вопрос не находит (проверяется и обратное: с passthrough-переписыванием — «не найдено»). Провайдер переписывания в тесте — тот же скриптованный инференс, что и у цикла (как в корне).
- Метрики: вызов переписывания идёт через `MeteredInferenceProvider` → событие `llm_call` с request_id запуска; юнит-тест `tests/unit/test_query_rewriter.py` проверяет событие и отсутствие содержимого запроса/реплик в JSONL и structlog-дубликате; аналогичная проверка на сбое переписывания — в E2E.
- Тесты: юнит инструмента (`tests/unit/application/test_search_tool.py`: переписывание до поиска, фолбэк при сбое, отсутствие содержимого в логах), прокидывание реплик (`tests/unit/application/test_service.py`, `ExecutionContext.recent_turns`), юнит `LlmQueryRewriter` (`tests/unit/test_query_rewriter.py`), E2E (`tests/integration/test_search_tool.py`).
- Документация: примечание в таблице контрактов `docs/architecture.md` дополнено (финальная правка текста — тикет 07).
- Гейты: `uv run ty check`, `uv run ruff check .`, `uv run ruff format --check .`, `uv run pytest` — 438 passed.
- Ревью (две оси параллельно): жёстких нарушений нет; две находки P2 отклонены с обоснованием. (1) «LlmQueryRewriter в main.py — Divergent Change, тесты импортируют bot.main»: тикет прямо требует реализацию в композиционном корне; вынос в rag-слой добавил бы rag зависимость от чат-модели.
