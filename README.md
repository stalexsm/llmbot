# Telegram LLM Bot

Telegram-бот на Python поверх локальной языковой модели [Ollama](https://ollama.com),
превращённый в минимального автономного агента: модель не только отвечает текстом,
но и сама выполняет консольные команды на машине пользователя
(инструмент execute_command) и пользуется скиллами — markdown-файлами с
готовыми инструкциями для типовых задач.

Возможности:

- **чат-сессия** — история каждого чата хранится на диске и подмешивается к
  запросу: бот помнит контекст диалога и переживает перезапуск;
- **агентный цикл** — модель либо даёт финальный ответ, либо вызывает
  execute_command, видит результат и продолжает; лимит шагов защищает от
  зацикливания, при исчерпании пользователь получает честное сообщение об
  остановке; tool-выводы шагов старше последних K схлопываются в сигнатуру
  «команда → ok/ошибка» (компакция), чтобы не раздувать контекст;
- **инструмент execute_command** — одна shell-команда из корня проекта;
  модель получает exit code, stdout и stderr (вывод чистится от ANSI-кодов
  и прогресс-шума, обрезается с сохранением головы и хвоста); зависшая
  команда обрывается по таймауту вместе с группой процессов;
- **скиллы** — каталог `skills/<имя>/SKILL.md`: системный промпт содержит только
  индекс (имя + краткое описание), полный текст модель читает сама через
  execute_command. Новый скилл добавляется файлом, без правки кода;
- **работа с документами (RAG)** — пользователь присылает боту файл
  (`.txt`, `.md`, `.docx`, `.pdf`), документ индексируется в локальную
  векторную БД (SQLite + sqlite-vec); содержательный вопрос агент сначала
  проверяет поиском по документам `search_documents`: нашёл — отвечает
  с указанием источника, не нашёл — отвечает как обычно, не выдавая домыслы
  за содержимое документов;
- **/new** — команда начинает новую чат-сессию: старая история отбрасывается;
- **/clear** — команда очищает корпус документов пользователя: удаляются все его документы с чанками и эмбеддингами;
- выполняемые команды в чат не выводятся (внутренняя кухня агента);
  длинные ответы разбиваются на несколько сообщений по границам строк.

## Архитектура

```text
Telegram (aiogram adapter)                сплиттер длинных ответов
        ↓
ApplicationService (use case: ProcessUserMessage) ←→ ChatSessionStore (.data/chats.db · SQLite)
        ↓                                              + окно истории, блокировка на чат
                                                       + DocumentService (.data/rag.db: индексация,
                                                         /documents, /delete, /clear; блокировка на владельца)
AgentLoop (агентный цикл) —— Tool: ExecTool (shell, таймаут, чистка и обрезка вывода)
        |       \___ Tool: SearchDocumentsTool (поиск по документам владельца)
        |                     индекс скиллов в системном промпте
        ↓
InferenceProvider (Protocol)          EmbeddingProvider (Protocol)
        ↓                                     ↓
OllamaInferenceProvider (adapter)   OllamaEmbeddingProvider (/api/embed, bge-m3)
        ↓
Ollama /api/chat (non-streaming)        RagService → RagStore → rag.db (SQLite + sqlite-vec)
```

Ключевые принципы:

- слои общаются только через типизированные контракты:
  `Telegram ≠ Application ≠ Agent ≠ Inference ≠ Ollama`;
- Telegram-слой не знает про Ollama; application-слой — про aiogram; агентный
  цикл зависит от протокола `InferenceProvider`, а не от адаптера Ollama;
- исполнитель команд (`ExecTool`) отделён от цикла: цикл знает инструмент по
  `ToolSpec` (имя, параметры), как именно выполняется команда — его дело;
- никакого глобального изменяемого состояния: все объекты создаются в
  composition root (`src/bot/main.py`) и внедряются явно через конструкторы;
- семантические идентификаторы — `typing.NewType`, внутренние модели —
  неизменяемые `dataclass(frozen=True)`, роли — `StrEnum`;
- ошибки инфраструктуры маппятся в прикладные исключения и не попадают
  к пользователю в исходном виде.

Подробнее о границах слоёв — `docs/architecture.md`; решение осознанно оставить
exec без ограничений на команды зафиксировано в `docs/adr/0001-exec-tool-unrestricted.md`.

## Чат-сессии

История чат-сессий — SQLite-БД `.data/chats.db`, одна на все чаты:
таблица `messages(id, chat_id, role, content, created_at)`, строка на
сообщение диалога «пользователь ↔ финальный ответ». Вызовы инструментов
и их результаты в сессию не пишутся — они живут только внутри одного
агентного запуска (результат инструмента, особенно ошибка, в истории
сбивает модель на следующих ответах). Файл `.data/` исключён из git.
Схема — только миграции alembic (`src/bot/sessions/migrations/`, новая
ревизия — `alembic revision --autogenerate --rev-id ...`), применяются
при старте бота. Системный промпт на диске не живёт — собирается заново
при каждом запросе. В запрос уходит окно последних сообщений сессии
(`AGENT_HISTORY_MAX_MESSAGES`). Сообщения одного чата обрабатываются строго
последовательно, разные чаты — параллельно.

## Работа с документами (RAG)

Пользователь присылает боту файл `.txt`, `.md`, `.docx` или `.pdf` — документ
индексируется фоновой задачей с редактируемым статус-месседжем (извлечение →
N чанков → эмбеддинги → готово), после чего на вопросы по его содержимому
агент отвечает с опорой на найденные чанки и указанием источника
(`Источник: vacation_policy.md` или `Источник: company_policy.pdf, стр. 12`).
Если релевантной информации в документах нет — агент честно говорит об этом,
а не выдумывает ответ из общих знаний.

### Архитектура pipeline

```text
индексация:  Telegram document → скачивание → извлечение текста (pypdf /
             python-docx / чтение текста) → структурный чанкинг → эмбеддинги
             (bge-m3) → rag.db (SQLite: documents → chunks → vec0-векторы)

поиск:       вопрос (+ переписывание по контексту диалога) → эмбеддинг запроса →
             sqlite-vec KNN (косинус, переопрос) → фильтр по владельцу → top-K →
             инструмент search_documents → LLM строит ответ по найденному
```

RAG реализован самостоятельно — от извлечения текста до сборки контекста;
из библиотек используются только pypdf, python-docx, sqlite-vec и модель
эмбеддингов Ollama. Поиск по документам — обычный инструмент агента
(`search_documents`): модель сама решает, когда его вызвать, а не получает
весь корпус в системном промпте.

### Chunking

Структурный чанкинг: текст режется по границам блоков (абзацы, заголовки,
элементы списков), блоки склеиваются в чанки с целевым размером
**900 символов** (`RAG_CHUNK_TARGET_CHARS`) и overlap **150 символов**
(`RAG_CHUNK_OVERLAP_CHARS`); блок длиннее целевого режется по границам
предложений.

Почему так: 900 символов — это примерно абзац–два связного текста —
достаточно, чтобы чанк был самодостаточным фрагментом смысла (вопрос
«сколько дней отпуска» должен попадать в чанк вместе с самим числом), и
при этом достаточно мало, чтобы эмбеддинг чанка не усреднялся между разными
темами документа. Overlap 150 символов страхует от потери фактов на границе:
предложение, разрезанное между чанками, целиком попадает хотя бы в один
из них.

Слишком маленькие чанки (100–200 символов) теряют контекст: эмбеддинг
«Отпуск составляет 28 дней» без упоминания компании/типа документа хуже
матчится с реальными вопросами, а в контекст LLM попадает рваный текст.
Слишком большие (3000+ символов) размывают тему: один чанк про отпуска,
командировки и парковку получает «средний» эмбеддинг, который плохо
матчится с чем-либо конкретным, а K топ-чанков съедают контекст модели,
наполовину состоя из нерелевантного текста.

### Embeddings

Модель — **bge-m3** через Ollama (`OLLAMA_EMBED_MODEL`), размер вектора —
**1024**. Причины выбора: bge-m3 — сильная открытая модель с хорошим
качеством на русском языке (корпуса и вопросы здесь русскоязычные), она
однопроходная (query и document кодируются одной моделью) и доступна
локально через тот же Ollama, что и чат-модель — без внешних API и ключей.

### Retrieval

Метрика — **косинусная близость** (`distance_metric=cosine` в sqlite-vec;
для нормированных векторов bge-m3 это стандартный выбор), **K = 5**
(`RAG_SEARCH_TOP_K`) с внутренним переопросом ×4 (`RAG_SEARCH_OVERFETCH`):
KNN берётся по всей таблице векторов, затем фильтр по владельцу и отсечка
до top-K — так владелец-фильтр не съедает часть K у владельцев с малыми
корпусами. K=5 — компромисс: меньше — риск не найти нужный чанк при
нескольких похожих разделах, больше — контекст LLM загрязняется
нерелевантными чанками и растёт расход токенов.

Ниже порога близости **0.5** (`RAG_MIN_SIMILARITY`) поиск отвечает явное
«ничего не найдено» — это то, что держит агента от выдумывания ответа по
случайным чанкам. Порог откалиброван на evaluation-датасете: прогон
`uv run python -m bot.evaluation` показал худшее попадание 0.578 и лучшее
ложное срабатывание 0.437 (негативный вопрос мимо корпуса); 0.5 — середина
разделяющей полосы с запасом вниз.

### Storage

Отдельный SQLite-файл `.data/rag.db` (вне git; схема — только миграции
alembic, см. ADR-0003):

```text
documents(id, owner_id, name, kind, created_at)
    ↓ 1:N
chunks(id, document_id, position, text, page)   ← текст чанка и номер
    ↓ 1:1                                          страницы (для PDF)
chunk_vectors(chunk_id, embedding)               ← виртуальная таблица vec0,
                                                  sqlite-vec, 1024 dim, cosine
```

По результату поиска вектор отматчивается обратно до чанка, документа и
имени файла — источник ответа строится всегда. Повторная индексация того
же имени заменяет документ атомарно (одной транзакцией); сырой файл после
индексации не хранится.

### Security: изоляция владельцев

Каждый документ принадлежит владельцу — пользователю Telegram, от лица
которого он загружен. Поиск всегда фильтруется по `owner_id`: запрос в
sqlite-vec без фильтра владельца невозможен — owner_id входит в сам SQL
запроса (`WHERE d.owner_id = ?`), инструмент `search_documents` получает
владельца из контекста выполнения (`ExecutionContext`), а не из аргументов
модели, поэтому LLM физически не может попросить поиск по чужому корпусу.
Документы пользователя A никогда не участвуют в ответах пользователю B
(тест изоляции A/B — `tests/unit/rag/`).

### Ограничения

- один экземпляр бота — один общий корпус на всех: изоляция по владельцу
  есть, но корпус живёт в локальном файле на машине бота;
- порог близости откалиброван на русском evaluation-датасете из 6 вопросов;
  на других языках или доменах порог стоит перекалибровать тем же прогоном;
- поиск чисто векторный (гибридный поиск и реранкинг не реализованы),
  точный поиск по номерам/кодам может проигрывать полнотекстовому;
- сканированные PDF без текстового слоя не извлекаются (OCR отсутствует);
- извлечение таблиц из DOCX/PDF плоское: таблица превращается в строки текста.

### Evaluation

Датасет из шести вопросов по трём документам (пять с известным источником
и один негативный «мимо корпуса») и живой прогон против Ollama:

```bash
uv run python -m bot.evaluation
```

По каждому вопросу печатается вердикт, ожидаемый источник, найденные чанки
с близостью и началом текста, в конце — сводка попаданий и предложенный
порог. Без запущенного Ollama или без bge-m3 прогон честно пропускается.

## Скиллы

Раскладка — один каталог на скилл: `skills/<имя>/SKILL.md`. Шапка файла — YAML
frontmatter с полями `name` и `description`; запасной вариант без frontmatter —
строка `Description:` (имя тогда берётся из имени каталога). Индекс собирается
при каждом запуске бота и попадает в системный промпт вместе с правилами цикла;
полный текст скилла модель читает сама через execute_command (`cat skills/…`). В репозитории
есть пример — скилл `weather`: сводка погоды через публичный wttr.in.

## Безопасность

По умолчанию агент выполняет произвольные shell-команды без allowlist команд —
это осознанное решение для личной машины (см. ADR-0001). Сдерживающие механизмы:
таймаут команды, обрезка вывода, лимит шагов цикла. Главный внешний риск —
чужие люди в Telegram — закрывается allowlist'ом чатов (`TELEGRAM_ALLOWED_CHAT_IDS`):
заполнив его одним своим chat id, вы оставляете доступ только себе.
Команды в логах не пишутся (логируются только метрики); диалог сохраняется
в локальную чат-сессию (SQLite), сами команды и их вывод — не сохраняются.

### Бенчмарк

Headless-прогон фиксированного набора из 20 offline-детерминированных задач
(5 «из знаний», 5 одношаговых exec, 6 многошаговых по репозиторию,
4 смешанных) напрямую через агентный цикл против живого Ollama, без Telegram:

```bash
uv run python -m bot.benchmark
```

По каждой задаче — success, расход токенов и результат содержательной
проверки, в конце — сводка по набору. Метрики прогонов пишутся в общий
`.data/metrics/events.jsonl` и видны в отчёте `bot.report`; зафиксированная
точка отсчёта для сравнения до/после — `docs/benchmark-baseline.md`.

## Проверки

```bash
uv run ty check                  # проверка типов
uv run ruff check .              # линтер
uv run ruff format --check .     # форматирование
uv run pytest                    # тесты (Ollama и Telegram не требуются)
uv run pytest -m live            # живые тесты против настоящего Ollama (без него — скип)
uv run python -m bot.evaluation  # RAG evaluation против живого Ollama (пропуск без него)
```

### Живые тесты

Живые тесты (`tests/live/`, маркер `live`) гоняют настоящего агента против
работающего Ollama и из дефолтного прогона исключены: без запущенного сервера
они скипаются, а не падают. Модель и режим берутся из окружения (`.env`:
`OLLAMA_MODEL`, `OLLAMA_THINK`, `OLLAMA_NUM_CTX`); для RAG-smoke нужна модель
эмбеддингов (`ollama pull bge-m3`), для судьи — `OLLAMA_JUDGE_MODEL`
(по умолчанию основная модель).

```bash
uv run pytest -m live                               # все живые тесты
uv run pytest -m live tests/live/test_behavioral.py # поведенческий датасет (13 кейсов)
uv run pytest -m live tests/live/test_sla.py        # один файл
```

Состав: смоук провайдера и RAG-ядра, поведенческий датасет (джейлбрейк,
отказ от выдумок, память диалога), судья качества свободных ответов
(LLM-as-a-Judge) и SLA-тест задержки.

## Логирование

`structlog`, настройка выполняется в composition root, логгеры внедряются через
конструкторы. В логах — только идентификаторы и метрики (`request_id`, `model`,
`steps`, `duration_ms`, `status`), но не содержимое сообщений и команд
пользователя и не секреты.
