# ADR-0003: Чат-сессии хранятся в SQLite

- Статус: принято
- Дата: 2026-09-09

## Контекст

Вместе с RAG (домашнее задание «RAG для AI-агента») в проект приходит SQLite
с sqlite-vec для документов. История чат-сессий при этом хранилась как
append-only JSONL — файл на чат, строка на сообщение, битые строки пропускались.
Наличие второго хранилища-движка делает JSONL-формат сессий анахронизмом.

## Решение

`ChatSessionStore` переезжает на SQLite — отдельный файл `.data/chats.db`.
Документы живут в собственном `.data/rag.db`: слои `sessions/` и `rag/` владеют
каждый своим файлом, схемой и соединением, расширение sqlite-vec грузится только
на rag-соединение; rag-БД можно снести и пересобрать, не трогая историю.

Контракт хранилища (`load` / `append` / `reset`) не меняется — подменяется только
реализация; application-слой и тесты подмены не замечают. stdlib `sqlite3`,
синхронно, без `aiosqlite`. Схемой владеет только alembic: новая ревизия
создаётся исключительно `alembic revision --autogenerate --rev-id ...`
против метаданных `src/bot/sessions/schema.py` (SQLAlchemy Core — только для
миграций, рантайм его не использует); применяет их композиционный корень
один раз на старте, до первой операции — хранилище схему не создаёт.
Rag-слой унаследует тот же механизм для своей БД. Таблица `messages(id,
chat_id, role, content, created_at)`; чтение окна — `ORDER BY id DESC
LIMIT N`; `/new` — `DELETE` по `chat_id`. Хранимое не меняется: только
диалог «пользователь ↔ финальный ответ», без системных ролей и tool-обмена.

Существующие JSONL-истории не импортируются: это dev-данные локальной машины.

## Последствия

- Проблема битых строк исчезает как класс; появляется `created_at`, которого
  в JSONL не было.
- Схема версионируется миграциями: смена формата хранения — новая ревизия
  alembic, а не правка старой; ручной `CREATE TABLE` в коде запрещён.
- Упоминание JSONL-сессии в ADR-0001 и описание чат-сессий в
  `docs/architecture.md` обновляются при реализации.
- Метрики остаются в append-only JSONL (анализ: write-once-лог для человека и
  CLI-отчёта; выгоды БД на этом объёме неизмеримы, издержки конкретны — три
  разнородных типа событий, переписывание recorder/report, потеря `tail`/`jq`).
