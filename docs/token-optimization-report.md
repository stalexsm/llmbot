# Отчёт: оптимизации расхода токенов агента (PR №2)

Итог аудита токенов: три оптимизации контекста, внедренные поверх слоя
метрик (PR №1). Измерения — headless-бенчмарк из 20 offline-задач против
живого Ollama (`qwen3:1.7b`), метрики — JSONL-события `llm_call`/`tool_call`/
`run` и отчёт `uv run python -m bot.report`.

## Сводка до/после

| Прогон | Input | Output | Total | Повторный контекст | Success | Верных ответов |
|--------|------:|-------:|------:|-------------------:|--------:|---------------:|
| Baseline (до оптимизаций)      | 1762 | 420 | **2182** | 623 (35%) | 20/20 | 16/20 |
| + обрезка exec, компакция (07, 08) | 1534 | 403 | **1936** | 512 (33%) | 20/20 | 13/20 |
| + сжатие системного промпта (09)   | 1167 | 561 | **1728** | 413 (35%) | 20/20 | 13/20 |

Средние токены на запуск. Экономия против baseline: **total −20.8%
(2182 → 1728), input −33.8% (1762 → 1167)**. Guard качества: success rate
не деградировал (20/20 во всех прогонах, ноль дополнительных сбоев).

## Методика

- **Инструмент**: `uv run python -m bot.benchmark` — 20 фиксированных
  offline-задач (5 «из знаний», 5 одношаговых exec, 6 многошаговых по
  репозиторию, 4 смешанных) прогоняются напрямую через `AgentLoop` против
  живого Ollama, без Telegram и без сети. Сетевых задач нет: сравнение
  зависит только от наших изменений.
- **Единица**: запуск агента (один агентный цикл). Токены — сообщённые
  моделью счётчики всех шагов запуска (`usage` ответа `/api/chat`).
- **Метрики**: каждый вызов модели и инструмента пишется событием в
  `.data/metrics/events.jsonl` (декораторы на швах `InferenceProvider` и
  `Tool`), запуск агрегируется записью `run`. Между прогонами JSONL
  архивировался, чтобы прогоны не смешивались.
- **Success** — финальный ответ в пределах лимита шагов без ошибки;
  **верных ответов** — содержательная проверка чекером задачи (вторичный
  показатель, на success не влияет).
- **Guard качества**: не больше одного дополнительного сбоя (success)
  на наборе из 20 задач.
- Ограничение методики: один прогон задачи за прогоны, а `qwen3:1.7b`
  стохастичен (температура по умолчанию) — шаги, объём ответов и сами
  ответы плавают от прогона к прогону. Это учтено в интерпретации ниже.

## Три оптимизации

1. **Умная обрезка exec-вывода** (тикет 07, `src/bot/agent/output.py`):
   ANSI/прогресс-шум снимается, при превышении `AGENT_EXEC_MAX_OUTPUT_CHARS`
   сохраняются голова и хвост, середина схлопывается маркером.
2. **Компакция старших tool-выводов** (тикет 08, `src/bot/agent/loop.py`):
   при сборке запроса выводы инструментов шагов старше последних K
   (`AGENT_COMPACTION_KEEP_STEPS`, 3) схлопываются в сигнатуру
   «команда → ok/ошибка». Хранимая чат-сессия не меняется.
3. **Сжатие системного промпта** (тикет 09, `src/bot/agent/prompts.py`,
   `skills.py`, `exec.py`) — выбрана по данным промежуточного аудита (ниже).

Сжатие затронуло и секцию индекса скиллов в промпте (`skills.py`): сокращены
формулировки вокруг списка («Файлы скиллов лежат…» → «Скиллы — файлы…»);
сам список не менялся — как и раньше, имя + первое предложение описания
(такое усечение было в коде и до аудита), полный `SKILL.md` читается
моделью по требованию через exec. Файлы скиллов и их раскладка
не тронуты.

## Промежуточный аудит и выбор третьей оптимизации

После 07+08 средний запуск: input 1534 / output 403 / total 1936
(−11% к baseline). Дальше аудит показал:

- **Шаг 1 каждого запуска стоит 831–849 input-токенов** (knowledge-задачи
  с пустой историей и вопросом в ~15 токенов). Это системный промпт плюс
  JSON-схема инструмента — и это повторяется на каждом шаге каждого
  запуска. Замеры частями (точный счётчик промпта `/api/chat`):
  схема инструмента и шаблон чата ≈ 219, правила ≈ 240, секция `<tools>`
  в промпте ≈ 86 (полный дубликат схемы), индекс скиллов ≈ 165,
  блок даты ≈ 47.
- **Повторный контекст** — 33% input; после компакции рост контекста
  от шага к шагу линейный (шаг 2 добавляет 40–700 токенов вместо
  полного дублирования).
- **Выводы инструментов** после 07+08 — в среднем 73 оценочных токена
  на запуск (было 190); дальше жать нечего.

Кандидаты из спеки и вердикт по данным:

| Кандидат | Вердикт |
|----------|---------|
| Динамическое окно истории по токенам | В bench история пуста — измерить эффект нечем; в реальных чатах окно хранит только реплики диалога (без tool-обмена) и уже ограничено 20 сообщениями. Слабый рычаг. |
| Чтение обычных файлов фрагментами | Выводы cat/ls уже обрезаны (07) и съедают ~73 ток./запуск; инструкцию о фрагментах пришлось бы добавлять в промпт, платя теми же токенами. Слабый рычаг. |
| **Сжатие системного промпта** | Крупнейшая управляемая статья: ~840 токенов на каждом шаге. Выбрано. |

Внедрение: формулировки правил ужаты без потери смысла; секция `<tools>`
убрана (инструмент описан в JSON-схеме поля `tools`, которую Ollama сама
рендерит в шаблон чата); описание инструмента и параметра в схеме,
секция индекса скиллов и блок даты сокращены. Шаг 1 подешевел
**838 → 628 токенов (−25%)**. От чрезмерного сжатия страхуют тесты
`TestPromptBudget`: бюджет на размер статичной части и семантические
якоря (точная фраза честного отказа, имя инструмента, анти-эхо правило,
пример чтения скилла).

## Почему экономия ниже цели 30%

Цель спеки — ≥30% суммарных токенов (input+output). Факт: **−20.8% total**.

- По **input** — единственной оси, которой управляют наши рычаги, —
  экономия достигнута: **−33.8%** (1762 → 1167).
- Output — чистое поведение модели: рычагов без ущерба качеству у нас
  нет («отвечай кратко» в промпте уже был), а на `qwen3:1.7b` он
  шумит сильнее, чем даёт любая безопасная правка: в финальном прогоне
  модель на двух задачах ушла в дополнительные шаги/длинные ответы
  (e05: 1233 ток. вывода за счёт повторов curl; m03: длинный одношаговый
  ответ 873 ток.), тогда как в промежуточном прогоне те же задачи
  стоили 722 и 373. Разброс одного прогона ±150–200 ток./запуск
  сопоставим со всей остаточной экономией.
- Остаток input — пол (~628 ток./шаг): схема инструмента и шаблон чата
  (~220) плюс минимальный поведенческий промпт (~390). Дальнейшее
  сжатие формулировок угрожало поведению маленькой модели — то есть
  guard качества.

## Guard качества

- **Success rate 100% во всех трёх прогонах** — ноль дополнительных
  сбоев при лимите «не больше одного».
- Верных ответов: 16 → 13 (как в промежуточном, так и в финальном
  прогоне). Падение случилось между baseline и промежуточным прогоном,
  то есть до сжатия промпта, и частично компенсировалось встречными
  переходами (r06: «неверно» → «ок»; r02/r03 наоборот). На выборке 20
  задач у стохастичной 1.7B-модели это шум измерения, а не эффект
  конкретной оптимизации; критерием качества по спеке служит success.

## Настройки

Новых переменных окружения оптимизации не добавили: 07 действует через
прежний `AGENT_EXEC_MAX_OUTPUT_CHARS`, 08 — `AGENT_COMPACTION_KEEP_STEPS`,
сжатие промпта (09) — правка констант кода без конфигурации. Полный
список настроек — `docs/runtime.md` и `env.example`.

## Как воспроизвести

```sh
uv run python -m bot.benchmark            # прогон набора, сводка в stdout
uv run python -m bot.report               # агрегат по всем запускам
uv run python -m bot.report --task bench-r01   # timeline запуска
```

Требуется живой Ollama с моделью `qwen3:1.7b`. Прогон пишет метрики в
`.data/metrics/events.jsonl` (вне Git); для чистого сравнения архивируйте
файл между прогонами.
