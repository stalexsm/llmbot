# Архитектура: слои и границы

Центральный принцип: `Telegram ≠ Application ≠ Agent ≠ Inference ≠ Ollama`.
Зависимости направлены строго вниз: верхний слой знает нижний только через
типизированный контракт (DTO, `Protocol` или доменную модель), нижний про
верхний не знает ничего. Глобального изменяемого runtime-состояния нет — все
объекты собраны и связаны в композиционном корне (`src/bot/main.py`).

```text
                            пользователь Telegram
                                      ↓
    ┌─────────────────────────────────┴──────────────────────────────────┐
    │ 1 · Telegram-адаптер · src/bot/telegram/                           │
    │ aiogram: /start · /new · allowlist чатов · маппер Message ↔ DTO    │
    │ сплиттер длинных ответов                                           │
    └─────────────────────────────────┬──────────────────────────────────┘
                                      ↓
        UserMessageRequest / UserMessageResponse
    ┌────────────────────────────────────────────────────────────────────┐
    │ 2 · Application · src/bot/application/                             │
    │ ProcessUserMessage: окно истории · блокировка на чат · сброс /new  │
    └───────────────┬─────────────────────────────────────────┬──────────┘
                    ↓                                         ↓
      старт цикла                                        история
┌────────────────────────────────────────┐ ┌────────────────────────────────┐
│ 3 · Agent · src/bot/agent/             │ │ Чат-сессии · src/bot/sessions/ │
│ AgentLoop: шаг = один ответ модели;    │ │ ChatSessionStore:              │
│ вызовы инструментов → exec →           │ │ chats.db · SQLite · ADR-0003   │
│ следующий запрос; финальный ответ      │ │ .data/chats.db · вне git       │
│ или лимит шагов (честный флаг)         │ │ только диалог «пользователь ↔  │
│ системный промпт заново + индекс       │ │ финальный ответ» · окно window │
└────────┬──────────────────────────┬────┘ └────────────────────────────────┘
         ↓                          ↓
   InferenceProvider           команда
┌─────────┴──────────┐     ┌─────────┴──────────────────┐
│ 4 · Инференс       │     │ Исполнитель команд         │
│ InferenceProvider  │     │ ExecTool: shell · таймаут, │
│ (Protocol)         │     │ kill группы; обрезка вывода│
└─────────┬──────────┘     └────────────────────────────┘
          ↓
             HTTP
┌─────────┴─────────────────┐
│ Ollama adapter            │
│ httpx · native tool-calls │
└───────────────────────────┘
          ↓
             Ollama /api/chat
```

## Слои

### 1 · Telegram-адаптер — `src/bot/telegram/`

Принимает апдейты aiogram и превращает их в типизированный вход
application-слоя, и наоборот:

- команды `/start` и `/new`, текстовые сообщения; allowlist чатов
  (политика живёт в `Settings`, хендлер получает решённое множество);
- маппер `Message → UserMessageRequest`;
- разбивка длинных ответов на части телеграм-совместимой длины по границам строк.

О Ollama этот слой не знает ничего: ни URL, ни JSON, ни класса провайдера,
ни логики инференса.

### 2 · Application — `src/bot/application/`

Use case `ProcessUserMessage` и управление чат-сессией. Под блокировкой на
чат (сообщения одного чата строго последовательны, разные чаты — параллельно):
читает историю, режет окно последних N сообщений, запускает `AgentLoop`,
дописывает обмен в хранилище, возвращает ответ с флагом остановки по лимиту.
Здесь же `reset_session` для `/new` и прикладные исключения, в которые нижние
слои маппят свои инфраструктурные ошибки. Не знает объектов Telegram API
и JSON Ollama.

### 3 · Agent — харнесс модели — `src/bot/agent/`

`AgentLoop` крутит шаги «ответ модели → выполнение инструментов → следующий
запрос»: ответ с вызовами инструментов продолжает цикл, ответ без них —
финальный и завершает его. Исчерпание лимита шагов — штатная остановка с
флагом в результате, а не исключение. Неизвестное имя инструмента и сбой
команды цикл не рвут: модель получает текст результата и действует дальше.
Инструмент виден циклу только как доменный `ToolSpec`; исполнение скрыто за
контрактом `Protocol Tool`.

Системный промпт собирается заново на каждый запуск (`prompts.py`); секция
индекса скиллов достраивается в композиционном корне. Полный текст скилла
(`skills/<имя>/SKILL.md`) в промпт не попадает — модель читает файл сама
через exec.

**Исполнитель команд** — `ExecTool` (`src/bot/agent/exec.py`), единственный
исполнитель действий; в цикл он идёт обёрнутым в `MeteredTool` из метрик
(см. секцию «Метрики токенов»): одна строка shell в рабочем каталоге проекта;
таймаут
обрывает команду вместе с группой процессов; вывод (exit code, stdout, stderr)
суммарно обрезается до лимита символов. Любое завершение — `ToolResult`:
невалидные аргументы, таймаут и ненулевой exit code — это данные для
следующего шага модели, а не исключения.

### Метрики токенов — `src/bot/metrics/`

Учёт расхода токенов: обычный диалог оставляет измеримый след. Декоратор
`MeteredInferenceProvider` реализует Protocol `InferenceProvider` структурно
и подключается в композиционном корне поверх настоящего адаптера: на каждый
вызов модели (включая неудачный) он пишет событие `llm_call` — timestamp,
run id (`RequestId`), модель, номер шага, input/output токены, повторные
токены, латентность, оценку стоимости. По завершении Запуска агента
`ApplicationService` закрывает запуск через порт `RunMetrics` — пишется
агрегированная запись `run` (шаги, суммарные токены, суммарный повторный
контекст и его доля, длительность, success), суммы которой сходятся с
`llm_call` того же запуска. Повторные токены — честная прокси-метрика
повторно передаваемого контекста (данных кэша Ollama не существует):
общий префикс списков сообщений текущего и предыдущего дошедшего до модели
запроса того же запуска (`metrics/repeat.py`; промпт сбойного вызова «уже
виденным» не считается), в символах, откалиброванный точным счётчиком
промпт-токенов; в события идут только числа, содержимое сообщений не
записывается. Каждый вызов инструмента учитывает декоратор `MeteredTool`
на шве `Tool` (в цикл `ExecTool` идёт обёрнутым в него): событие `tool_call`
несёт класс команды `exec:<класс>` — `git`, `python`, `rg`, `cat`, `ls`
или `other` (чистый классификатор — `agent/command_class.py`), размеры
ввода/вывода в символах, длительность, оценку выходных токенов (~4 символа
на токен) и статус; содержимое команды и её вывода не записывается.
`RunMetricsCollector` копит вызовы по `RequestId`;
`MetricsRecorder` дописывает обе записи в append-only JSONL
(`.data/metrics/events.jsonl`) и дублирует их в structlog — по `request_id`
лог коррелирует с JSONL-строкой по request_id (а при сбое хранилища остаётся единственным следом вызова). События несут только счётчики и
идентификаторы: содержимое сообщений, команд и ответов модели в метрики
не попадает; сбой хранилища метрик работу бота не рвёт.

**CLI-dashboard** — `src/bot/report/` (точка входа `uv run python -m bot.report`):
автономный офлайн-отчёт поверх того же JSONL, вне графа зависимостей бота
(никаких Settings и секретов не требует). Рендер — чистая функция от событий:
`events.py` читает JSONL в типизированные записи (битые строки пропускаются,
отсутствующий файл — пустой отчёт), `aggregate.py` и `timeline.py` — чистая
агрегация (сводка по всем запускам и пошаговый timeline одного запуска
по `--task <id>`), `render.py` — отрисовка текста, `cli.py` — только разбор
аргументов и вывод в stdout.

**Headless-бенчмарк** — `src/bot/benchmark/` (точка входа `uv run python -m
bot.benchmark`): прогон фиксированного набора из 20 offline-задач напрямую
через агентный цикл против живого Ollama, без Telegram. Граф собирается
зеркально композиционному корню (Ollama → `TokenTrackingProvider` →
`MeteredInferenceProvider` → `AgentLoop`), поэтому метрики bench-запусков
видны в общем JSONL и CLI-dashboard. Baseline — `docs/benchmark-baseline.md`.

### Чат-сессии — `src/bot/sessions/`

`ChatSessionStore` — SQLite-БД `.data/chats.db`, один файл на все чаты
(вне git; ADR-0003): таблица `messages(id, chat_id, role, content,
created_at)` — строка на сообщение диалога «пользователь ↔ финальный
ответ». Системные роли и tool-обмен (вызовы инструментов и их результаты)
не хранятся: результат инструмента — особенно ошибка — в истории сбивает
модель на следующих ответах; tool-обмен живёт только внутри одного
агентного запуска. Схема — только миграции alembic (`migrations/`; новая
ревизия — `alembic revision --autogenerate --rev-id ...` против метаданных
`schema.py`), применяет их композиционый корень на старте; хранилище
работает на stdlib `sqlite3`, синхронно. Чтение окна — `ORDER BY id DESC
LIMIT N`, `/new` — `DELETE` по `chat_id`; история переживает рестарт
процесса, у каждого сообщения есть `created_at`. Сбой БД маппится на
`SessionStorageError` — пользователь получает заглушку, бот не
останавливается. Старые JSONL-файлы `.data/chats/` не импортируются и не
трогаются. Окно истории — чистые функции `window.py`. Блокировка на чат
живёт не здесь, а выше — в `ApplicationService`.

### 4 · Inference — `src/bot/inference/`

`provider.py` — `typing.Protocol`; приложение зависит только от протокола,
новый провайдер подключается без изменений application- и telegram-слоёв.
Адаптер `ollama.py`: HTTP-обмен httpx, сериализация запроса и нативные
tool-calls, Pydantic только на границе JSON, таймауты, маппинг инфраструктурных
ошибок на application-исключения. `httpx.AsyncClient` инжектится извне и
переиспользуется всё время жизни процесса.

## Контракты между слоями

| Контракт | Где живёт | Кто даёт гарантию | Кто потребляет |
|---|---|---|---|
| `UserMessageRequest` / `UserMessageResponse` | `application/models.py` | маппер Telegram | `ApplicationService` |
| `InferenceMessage`, `MessageRole` | `domain/messages.py` | домен | все слои |
| `ToolSpec` / `ToolCall` / `ToolResult` | `domain/tools.py` | домен; заполняет `ExecTool` | `AgentLoop` |
| `Tool` (Protocol) | `agent/tools.py` | реализует `ExecTool`, в цикл идёт обёрнутым в `MeteredTool` | `AgentLoop` |
| `InferenceProvider` (Protocol) | `inference/provider.py` | реализует адаптер Ollama и декоратор метрик | `AgentLoop` |
| `RunMetrics` (Protocol) | `metrics/collector.py` | реализует `RunMetricsCollector` | `ApplicationService` |
| `AgentProgress` (Protocol) | `agent/progress.py` | реализует `NullProgress` (заглушка: выполнения команд в чат не выводятся) | `ExecTool` |
| `ApplicationError` и подтипы | `application/errors.py` | кидают нижние слои | Telegram-слой |

Выполняемые команды в чат не выводятся (внутренняя кухня агента, та же
политика сокрытия, что и для логов): `ExecTool` отчитывается прогрессу,
по умолчанию это заглушка `NullProgress`.

## Поток одного сообщения

1. Хендлер проверяет allowlist; маппер строит `UserMessageRequest`
   с новым `RequestId`.
2. `ApplicationService` берёт блокировку чата.
3. История читается из SQLite окном последних сообщений (`ORDER BY id DESC
   LIMIT N`) и режется до окна (`window.py`).
4. Шаг `k` цикла: запрос = свежий системный промпт + окно истории +
   обмен текущего запуска; в запросе — спецификации инструментов.
5. Ответ без вызовов инструментов — финальный: в БД сессии дописывается
   диалог обмена (сообщение пользователя и финальный ответ; tool-пары
   не сохраняются), текст уходит пользователю (со сплиттером длинных ответов).
6. Ответ с вызовами: сообщение ассистента попадает в обмен; каждый вызов —
   исполнение `ExecTool`, результат модели сообщением роли `tool` — и
   следующий шаг.
7. Лимит шагов исчерпан → пользователь получает честное сообщение
   об остановке (его текст принадлежит Telegram-слою). Команда `/new`
   сбрасывает сессию под той же блокировкой чата.

## Композиционный корень и внедрение зависимостей

- Зависимости внедряются явно, через конструкторы. Компонент создаёт свои
  инфраструктурные зависимости только снаружи — сам себе их не конструирует
  (`ApplicationService` не создаёт `OllamaInferenceProvider`).
- DI-контейнер (Dishka) не используется: сборка ручная, в композиционном
  корне. Введение контейнера не должно требовать изменений
  domain/application-контрактов.
- Корень — `run()` в `src/bot/main.py`: Settings → httpx-клиент →
  OllamaInferenceProvider → MeteredInferenceProvider → ExecTool → MeteredTool →
  индекс скиллов + системный промпт → AgentLoop → ChatSessionStore →
  ApplicationService → Bot/Dispatcher → polling.
- Владение жизненным циклом явное: HTTP-клиент и сессия бота закрываются
  в `finally`.

## Ошибки на границах

- Инфраструктурные ошибки остаются вне application-слоя: адаптер Ollama
  маппит HTTP/сеть/таймауты на `InferenceError`, `InferenceTimeoutError`,
  `InferenceUnavailableError`.
- Telegram-слой превращает application-ошибки в безопасные сообщения:
  raw-исключения, стеки, URL и детали инфраструктуры доходят до пользователя
  только текстом-заглушкой.
- Сбои выполнения команды внутри цикла наружу не выходят: исполнитель всегда
  возвращает `ToolResult`, модель сама решает, что делать дальше.
- Сбой хранилища сессии маппится в `SessionStorageError`; пользователь видит
  заглушку, сессия не портится — недописанный обмен просто не сохраняется.
- Исчерпание лимита шагов — не ошибка, а штатная остановка с флагом
  `stopped_by_limit`.
